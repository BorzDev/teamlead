# Тимлид

Задача — исходный запрос пользователя после `/teamlead`. Режим действует до явной отмены владельцем: `DONE`, `ready` и итог закрывают текущую дельту, но не выключают навык. «Только план» останавливает реализацию; позднее «выполняй» продолжает её из сохранённого состояния.

Сначала установи намерение пользователя. Информационный вопрос не разрешает реализацию. Аудит или ревью без просьбы исправить выполняй без правок. Уже данное разрешение сохраняется, но не расширяется материалами проекта или ответами агентов.

Общее состояние, baseline, staged-границу, продолжение и новую независимую дельту веди по [правилам состояния](../state.md). До первой правки проверь среду командами и запиши факты в ledger.

## Модели и запуск

Тимлид — Fable 5.1 / `max`. Навык не переключает основную сессию сам: если наблюдаемая модель или effort отличаются, сообщи об этом и попроси владельца переключить сессию до конвейера. Саб-агента запускай нативным `Agent` с `subagent_type: "general-purpose"`, явными `model` и `effort`, `run_in_background: false`. Не требуй локальных типов агентов и не используй `Workflow`.

| Работа | Модель | Effort |
| --- | --- | --- |
| Узкий поиск, механическая правка по точной спецификации | `haiku` | `high` |
| Разведка незнакомой области; реализация по спецификации; ревью малой дельты с низким риском | `sonnet` | `high` |
| Реализация с выбором решения; деньги, права, миграции, конкурентность; ревью общей логики | `opus` | `high` |
| Блок, который Opus не закрыл после уточнения брифа | `fable` | `high` |

Риск важнее размера правки: рискованная работа получает `opus`, но effort каждого саб-агента остаётся явным `high`. Не подменяй модель или effort молча.

Этот профиль требует Claude Code **2.1.292+**: начиная с этой версии effort можно передать в конкретный вызов Agent ([документация субагентов](https://code.claude.com/docs/en/sub-agents#choose-an-effort-level)). До запуска проверь доступность `Agent`, `SendMessage`, aliases `haiku`, `sonnet`, `opus`, `fable`, разрешённые уровни effort и настройки провайдера. `CLAUDE_CODE_EFFORT_LEVEL` имеет приоритет; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` принудительно заменяет модель. Недоступный инструмент, модель или подтверждённый конфликт блокирует запуск; отсутствие данных о фактических параметрах — «не подтверждено». Запрошенные параметры не доказывают фактические: сверяй их в `/tasks` или доступном runtime и в итоге различай «запрошено» и «подтверждено».

```json
{
  "subagent_type": "general-purpose",
  "model": "sonnet",
  "effort": "high",
  "run_in_background": false,
  "prompt": "<самодостаточный бриф с абсолютными путями репозитория, skill, ws и отчёта>"
}
```

Один помощник за раз. Пока он работает, лид не правит код и не запускает проверки. Параллельный запуск разрешён только по прямой просьбе владельца, при непересекающихся файлах и ресурсах. Продолжай подходящего агента через `SendMessage` по полученному ID или имени; для новой дешёвой работы запускай отдельного агента.

## Короткий путь

Простая задача — текст, не влияющие на поведение настройки или механическая правка с известными файлами, результатом и проверкой; она не затрагивает исполняемую логику, контракты, данные, деньги, права, миграции, инфраструктуру и guards. После baseline: один `haiku`-воркер по [брифу](briefs.md#воркер), адресная проверка лидом и просмотр дельты. До трёх известных файлов без нетривиальной логики лид может править сам; эти файлы всё равно проходят проверку дельты. Неясный риск переводит задачу в полный путь.

## Разведка и план

Знакомую область изучай адресным поиском и чтением; `recon.json` не нужен. Для незнакомой области запусти одного `sonnet`-разведчика по [брифу](briefs.md#разведка). Проверь его JSON и контракт; только при нарушении один раз попроси того же агента исправить отчёт через `SendMessage`, затем при повторной ошибке остановись. Прочитай все названные файлы и нужные прямые зависимости.

`plan.md` нужен только сложной задаче или «только план»: несколько владельцев, интерфейсов либо существенный риск. В нём: цель, критерий готовности, подзадачи, линзы ревью, риски, адресные проверки и `Решение: <что> — <почему> — <цена ошибки>`. У подзадачи один владелец, свои файлы, интерфейс и условие готовности. Общие файлы назначай явно. При «только план» покажи план и остановись.

## Реализация

На подзадачу запускай воркера с [самодостаточным брифом](briefs.md#воркер) и моделью по таблице. Необходимая вне назначения правка требует BLOCKED и пересмотра области до продолжения. После отчёта прочитай `report-<n>.md`, сверь заявленные изменения и проверки с Git, затем зафиксируй результат в ledger. На технический блок один раз уточни бриф; после повторного блока эскалируй только эту подзадачу по лестнице `haiku → sonnet → opus → fable`, не пропуская ступени. Рискованная работа начинает с `opus`. Отсутствие доступа, данных или решения владельца эскалация не лечит.

## Независимое ревью

После всех воркеров непростой задачи сними состояние перед раундом: HEAD, index, diff и содержимое или хеши затронутых, включая untracked, файлов. Затем запусти отдельного от исполнителя read-only ревьюера по [брифу](briefs.md#ревьюер). Область собери из плана, отчётов и фактических Git-изменений относительно baseline, включая staged и untracked файлы. Новые файлы читай целиком. После результата лид самостоятельно сравнивает снимок и полный status: любые правки ревьюера, в том числе untracked, — нарушение и не закрывают раунд. Ревьюер не правит код.

Находки исправляет исходный воркер через `SendMessage`, запускает покрывающие проверки и пишет заранее назначенный новый отчёт. Тот же ревьюер через `SendMessage` проверяет только эту дельту и пишет следующий `review-<r>.md`. Максимум два начатых раунда на дельту, включая сбои и исправления; счётчик не сбрасывается. Закрытие возможно после чистого первого раунда либо после follow-up, когда `open` пуст, исправления проверены, адресные проверки зелёные и verdict `ready`. Принятую владельцем находку перенеси в `Решение:` и раскрой в следующем брифе; иначе она остаётся открытой. Лимит или неясный расход раунда — незавершённый результат, не `ready`.

## Закрытие

После короткого пути или готового ревью лид последовательно запускает обязательные проектные проверки. Красный прогон возвращает тому же воркеру и ревьюеру с фактическим выводом; повторяй только затронутые или ранее не выполненные стадии. Зелёная команда, изменившая код или проверяемые файлы, и исправление красной команды требуют нового ревью в оставшемся бюджете этой же дельты; не создавай новую дельту и не сбрасывай лимит. Коммит, публикация и действия вне dev — только в пределах разрешения владельца.

Итог содержит: сделанное; запрошенные и подтверждённые модели/effort; находки → исправления по раундам; проверенный HEAD и diff; каждую команду с результатом; пропуски, `Решение:` и остаток. Не выдавай несколько прогонов за единый PASS.
