# Тимлид для Codex

Профиль Codex для навыка `teamlead`. Задача — запрос пользователя после `$teamlead`; указание «только план» или `plan only` завершает работу после плана. Основная сессия ведёт проект и принимает решения, саб-агенты ищут код, реализуют, проверяют и исправляют его.

## Модели и запуск

Лид — `gpt-6-astra`, effort `ultra`. Навык сам не переключает модель основной сессии: запускай его с Astra / Ultra в Codex. Если активная сессия явно использует другую модель или effort, сообщи об этом и запроси переключение до запуска конвейера. Значения в `config.toml` — настройки по умолчанию, а не доказательство модели уже открытой сессии.

| Работа | model | reasoning_effort |
|---|---|---|
| Узкая разведка, механические правки по точной спецификации | `gpt-5.6-luna` | `medium` |
| Разведка неизвестной области или нескольких связанных модулей | `gpt-5.6-terra` | `medium` |
| Основная реализация | `gpt-5.6-terra` | `high` |
| Обычный независимый раунд ревью | `gpt-5.6-sol` | `high` |
| Реализация и ревью: сложные миграции, деньги, авторизация, конкурентные изменения | `gpt-5.6-sol` | `xhigh` |
| Отдельный блок, с которым Sol не справилась после уточнения задачи | `gpt-6-astra` | `ultra` |

Это стартовая стратегия, а не доказанный оптимум стоимости. Выбирай по сложности и последствиям ошибки; квоты на долю моделей нет. Luna получает ограниченные задачи с проверяемым результатом. Для неизменного запуска готовой команды проверки достаточно Luna / low; диагностику красного прогона передавай исполнителю или ревьюеру.

Перед делегированием прочитай [правила состояния](../state.md) и [briefs.md](briefs.md). Используй реальные инструменты `collaboration`: отдельный вызов `spawn_agent` для каждого нового агента, `fork_turns: "none"`, явные `model` и `reasoning_effort` из таблицы. Полный fork наследует дорогую модель и не принимает overrides. В `message` передавай самодостаточный бриф с абсолютными путями репозитория, навыка, рабочей папки и назначенных артефактов. Пример вызова `collaboration.spawn_agent`:

```json
{
  "task_name": "implement_1",
  "fork_turns": "none",
  "model": "gpt-5.6-terra",
  "reasoning_effort": "high",
  "message": "<полный бриф воркера из briefs.md с подставленными путями и заданием>"
}
```

Вызывай collaboration напрямую, вне `functions.exec`. Для текущего агента используй `send_message`, для продолжения его работы — `followup_task`, для ожидания уведомления — `wait_agent`; сам результат читай из сообщения агента и назначенного файла. Проверяй доступные инструменты и лимит параллельности текущей сессии; при четырёх общих слотах лид оставляет до трёх воркеров. Ограничение слотов обрабатывай очередью. Отсутствие модели или инструмента обозначай явно; не подменяй запрошенную модель молча. Пользовательские задачи через `create_thread` для подзадач не создавай.

До каждого запуска сохрани в ledger стартовую запись, уникальный `task_name`, назначенный путь результата и запрошенные model/effort; полученный ID агента добавь сразу после `spawn_agent`. Для ревью также заранее расходуется номер раунда. Если после сбоя нельзя восстановить идентичность активного агента или расход раундов, остановись с незавершённым результатом: не создавай дубликат и не обнуляй счётчик.

Принимай результат агента после открытия назначенного файла в `<ws>`: путь бери из брифа и ledger, а не только из сообщения агента. Первые пути — `recon.json`, `report-<n>.md` и `review-<r>.md`. Если в сообщении путь ошибочен, но ожидаемый файл записан правильно, используй проверенный файл и отметь расхождение в ledger. Для отсутствующего, нечитаемого или невалидного результата разрешён суммарно один корректирующий `followup_task` тому же агенту; назначь новый путь, например `report-<n>-retry-1.md`, сохрани исходный артефакт и передай конкретное нарушение. После повторного сбоя запиши BLOCKED и причину, зависимую стадию не начинай. Недоступность записи, модели, инструмента, входных данных или требуемого решения — внешний блокер: сразу обозначь BLOCKED без неизменных повторов. Закончи доступную независимую работу и сообщи остаток. Счётчики попыток сохраняй при продолжении. Принятые пути результатов фиксируй в ledger и подставляй в последующие брифы.

## 1. Рабочее состояние и разведка

До разведки прочитай применимые `AGENTS.md`/`CLAUDE.md` и выполни [правила состояния](../state.md): проверь идентичность запуска, создай либо явно продолжи `<ws>`, зафиксируй исходные HEAD, индекс, рабочее дерево и untracked. Корень отчётов Codex — `${CODEX_HOME:-$HOME/.codex}/teamlead/`; правила выбора `repo-key`/идентификатора запуска, размещения вне репозитория, снимков и продолжения заданы в общем документе. Baseline повторно не создавай и не заменяй при продолжении. Необъяснимые параллельные изменения согласуй с их владельцем.

Первый разведчик по брифу пишет `recon.json`, не больше 40 записей: точки входа, владельцы поведения, переиспользуемые решения, тесты, контракты, обязательные документы, риски и неизвестное. Лид читает найденные файлы и относящиеся к задаче прямые зависимости; пробелы закрывает узким заданием следующему разведчику с новым путём recon. Принятые дополнительные результаты укажи в плане для следующих исполнителей. Разведка закончена, когда известны реальные вызывающие пути, место изменения и способ проверить результат.

Перед планированием проверь назначенный recon JSON-парсером и проверь структуру по контракту раздела «Разведчик» в [briefs.md](briefs.md): обязательные ключи, типы полей, допустимые роли, лимит записей и существование указанных файлов. Валидный синтаксис JSON сам по себе недостаточен. При ошибке используй единственный корректирующий повтор из правил приёма результата; более дорогая модель не сбрасывает этот лимит. В ledger зафиксируй результат и принятый путь recon; переход к плану разрешён после успешной проверки.

## 2. План

В `plan.md` запиши цель, проверяемое условие готовности, подзадачи, линзы ревью и риски. Для каждой подзадачи задай модель/effort, выделенные файлы, интерфейсы и адресные проверки из правил проекта. Общие файлы (снапшоты, i18n, инварианты, индексы) назначь одному владельцу. Допущения фиксируй как `Решение: <что> — <почему> — <цена ошибки>`; решения, влияющие на реализацию, внеси в план и ledger.

Готово, когда каждая подзадача имеет владельца, границы файлов и проверку. При «только план» или `plan only` покажи план и остановись до реализации и проверок с побочными эффектами.

Для аудита без исправлений зафиксируй режим `read_only` и пустой `writeFiles`, пропусти реализацию и передай ревьюеру только область чтения: аудит завершается принятым отчётом с находками и ограничениями, без требования нулевых findings, цикла исправлений и финальных проверок с побочными эффектами.

## 3. Реализация

Назначь воркера на подзадачу; мелкие связанные правки объединяй. Параллель разрешён только для непересекающихся файлов и независимых ресурсов: одинаковые БД, миграционные каталоги и генерируемые файлы также считаются пересечением. При необходимости нового файла воркер возвращает `request_scope`; лид согласует новую границу с другими работами до продолжения.

Воркеры пишут назначенные отчёты, запускают адресные проверки и возвращают DONE или BLOCKED. Лид фиксирует результат в ledger, сомнения переносит в линзы ревью. Внутренний `request_scope` разреши пересмотром назначения в пределах пользовательской задачи до новых правок; зависимость от недоступного доступа, данных или пользовательского решения сразу обозначь внешним BLOCKED. При техническом провале допускается одно уточнение и один повтор на текущем уровне модели, затем эскалация только этой подзадачи: Luna → Terra → Sol → Astra, с effort из таблицы; для рискованной работы Sol всегда xhigh. Повторный провал Astra после одного уточнения завершает эту подзадачу как BLOCKED с результатами попыток и остатком. Не начинай цепочку заново; счётчики храни в ledger. Новым попыткам назначай новые пути отчётов. Это не увеличивает отдельный лимит исправления невалидного артефакта.

Лид не дописывает код за воркера: даже маленькое исправление получает исполнителя и независимое ревью. Реализация закончена после DONE всех подзадач и чтения их отчётов лидом.

## 4. Независимое ревью

Используй native collaboration, отдельный свежий Sol с `fork_turns: "none"` на каждый раунд: high для обычного ревью, xhigh для денег, авторизации, сложных миграций и конкурентных изменений. Effort выбери по области раунда и запиши до запуска. Claude `Workflow` и модель `opus` здесь не используются. Перед ревью дождись завершения всех воркеров; пока ревьюер исправляет код, другие агенты его не редактируют.

Перед каждым раундом пересобери область из плана, отчётов воркеров, прошлых ревью и текущих `git status`/`git diff` относительно baseline. Учитывай новые, удалённые, переименованные и исходно изменённые файлы: изменение уже dirty-файла не обнаруживается одним сравнением списка status. Новые файлы читай целиком. Сохрани состояние перед раундом: HEAD, индекс, diff и содержимое либо хеши затронутых файлов, включая untracked. После завершения самостоятельно сравни состояние и полный status с этим снимком; проверь появившиеся файлы и любые расхождения с отчётом. Не доверяй только полю `touched` агента.

Ревьюер читает спецификацию и код с вызывающими путями, при разрешённой реализации сам исправляет реальные дефекты в `writeFiles` и проверяет исправления; в `read_only` только описывает находки, вкус и стиль не считаются находками. Отчёт — назначенный `review-<r>.md`: findings, fixed, open, touched, checks, verdict. Лид проверяет отчёт и записывает в ledger `Ревью <r>: <найдено> → <исправлено>, <вердикт>`. Номер резервируется и расходуется в ledger до запуска, существующие отчёты не перезаписываются. Если при разрешённых исправлениях есть `open/request_scope`, лид согласует расширение в рамках задачи, обновляет план и снимки исходных файлов до правок; следующий аудит выполняет свежий ревьюер с новым номером. Исправляющий повтор отчёта того же агента разрешает только оформление уже полученного результата: новый аудит или новые правки кода требуют нового раунда.

Успех цикла исправлений — отдельный раунд с нулём findings, пустым open, зелёными обязательными для раунда проверками, verdict `ready` и подтверждённым отсутствием правок к проверяемому результату за этот раунд. Любые фактические правки, даже при нулевых findings в отчёте, требуют следующего свежего ревью. Максимум шесть начатых раундов на задачу, включая сорванные запуски и повторное ревью после финальных проверок; счётчик сохраняется при продолжении. Нет принятого отчёта после разрешённого исправления, сорвался агент или достигнут лимит без чистого раунда — это незавершённая проверка: укажи причину и остаток, не объявляй ready. При неизвестном расходе после сбоя остановись, не восстанавливай нулевой счётчик по отсутствию файлов.

## 5. Финальные проверки и результат

После чистого ревью назначь запуск всех необходимых проектных стадий для затронутого поведения. Следуй документу тестирования из `AGENTS.md`/`CLAUDE.md`, при его отсутствии — фактическим командам сборки и тестов. Финальные стадии выполняй последовательно: они могут делить БД и каталог миграций. Длительные shell-команды веди через доступную exec-сессию и последующее чтение её результата, сохраняя обновления для пользователя. Сверь итоговое состояние с проверенным ревью: если даже зелёная команда изменила результат задачи, ему требуется свежий раунд в оставшемся лимите и проверки затронутого поведения.

Красный прогон из-за дефекта передавай свежему ревьюеру с результатом команды, только если остался лимит раундов. Рискованная область сохраняет Sol / xhigh. Внешнюю причину без доступного решения фиксируй как BLOCKED без повторного ревью неизменного состояния. После исправления обязателен новый чистый раунд в общем лимите; затем повтори упавшие, затронутые и ранее пропущенные стадии. Прежний PASS используй только при подтверждённой неизменности соответствующего кода и окружения. Обязательные gates и ограничения проекта сохраняются. Выполни проектный чеклист закрытия, если он есть.

Итог: что сделано, запрошенные модели/effort и отдельно подтверждённые средой фактические значения, найдено → исправлено по раундам, проверенный HEAD и diff поверх него, команды и результаты, пропуски, решения и остаток. Если среда не сообщает фактическую модель/effort, напиши «не подтверждено»; аргументы запуска не доказывают фактические значения. Проверь сохранность исходных HEAD и индекса по [правилам состояния](../state.md). Коммит, публикация и действия вне dev выполняются только в пределах разрешения пользователя; при разрешённом коммите сохраняй исходное содержимое индекса и включай только согласованные изменения конвейера. Навык сам не расширяет полномочия. Уже данное разрешение повторно не спрашивай. Если входных данных недостаточно для следующего решения, закончи независимую работу и задай конкретный вопрос.
