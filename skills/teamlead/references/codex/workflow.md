# Тимлид для Codex

Режим `teamlead` действует до отмены пользователя. Итог закрывает задание, не режим; следующую работу задаёт пользователь. «Только план» / `plan only` заканчивается планом; «выполняй» продолжает его. Разделы ниже применяй по необходимости, а не как обязательный конвейер. Информационный вопрос не разрешает реализацию; аудит без просьбы исправить выполняй только чтением.

## Модели и запуск

Лид — `gpt-6-astra`, effort `ultra`. Навык сам не переключает основную сессию. Если она явно использует другую модель или effort, сообщи и запроси переключение перед делегированием; настройки по умолчанию не доказывают параметры открытой сессии.

| Работа | model | reasoning_effort |
| --- | --- | --- |
| Узкая разведка, механические правки по точной спецификации | `gpt-6-luna` | `medium` |
| Разведка незнакомой области; реализация по спецификации | `gpt-6.1-sol` | `high` |
| Независимое ревью | `gpt-6.1-sol` | `high` |
| Реализация и ревью: деньги, права, сложные миграции, конкурентность | `gpt-6.1-sol` | `xhigh` |
| Отдельный блок, который Sol не закрыла после уточнения брифа | `gpt-6-astra` | `ultra` |

Риск важнее размера правки. Это стартовая стратегия, не измеренный оптимум стоимости. Доступность сверяй с текущим runtime: не подменяй отсутствующую модель молча. Модели и усилия в Codex могут отличаться от API; [документация Codex](https://learn.chatgpt.com/docs/models) и фактическая схема инструмента определяют допустимые параметры.

Прочитай [правила состояния](../state.md) и [брифы](briefs.md). Запускай `collaboration.spawn_agent` напрямую, вне `functions.exec`, с `fork_turns: "none"`, явными `model` и `reasoning_effort`. Полный fork наследует модель и не допускает overrides. Каждый бриф самодостаточен: абсолютные пути, цель, критерий, область записи, известные факты среды и принятые решения.

```json
{
  "task_name": "implement_1",
  "fork_turns": "none",
  "model": "gpt-6.1-sol",
  "reasoning_effort": "high",
  "message": "<самодостаточный бриф воркера с абсолютными путями и назначенным отчётом>"
}
```

Связанную работу продолжай через `followup_task` с ID/именем агента, пока его модель подходит роли. `send_message` передаёт уточнение работающему агенту; `wait_agent` ждёт уведомление, результат читай из сообщения и назначенного файла. Дешёвую новую работу передавай подходящей дешёвой модели. Пользовательские чаты через `create_thread` для подзадач не создавай.

Один помощник за раз; пока он работает, сам не правь файлы и не запускай проверки. Параллель — только по прямой просьбе пользователя, с отдельными областями файлов и ресурсов, в пределах реальных слотов. Ограничение слотов обрабатывай очередью. Одну готовую команду проверки запускай сам: отдельный агент ради команды не нужен.

## Состояние и выбор пути

До первой правки прочитай применимые `AGENTS.md`/`CLAUDE.md` и сохрани baseline по [state.md](../state.md). Проверь командами нужную среду: тест-раннер, команды проверок, runtime, зависимости, БД и dev-сервер, если задача их использует. Запиши `Среда:` в ledger и передавай факты агентам; отсутствие среды без проверки не повод пропустить стадию.

Простая задача — текст, настройки без влияния на поведение или механическая правка с известными файлами, результатом и проверкой. Она не затрагивает исполняемую логику, контракты, данные, деньги, права, миграции, инфраструктуру и guards. Путь: baseline → один воркер Luna (до трёх файлов без новой логики правь сам) → адресная проверка → просмотр дельты лидом. `recon.json`, `plan.md` и отдельный ревьюер не нужны. Неясны границы или риск — обычный путь.

Если область знакома, используй адресный `rg` и чтение, передай файлы и паттерны в брифе. Иначе назначь одного разведчика Sol; проверь `recon.json` парсером и по контракту брифа, прочитай указанные файлы, относящиеся к решению.

План в `plan.md` нужен для сложной задачи (несколько владельцев, интерфейсов или существенный риск) и всегда в режиме «только план». В остальных случаях цель, файлы, критерий и проверки достаточно записать в ledger и брифе. План содержит подзадачи с владельцами, интерфейсами и проверками, линзы ревью и риски; общие файлы вроде i18n, barrel-index и снапшотов перечисляй явно. Решения записывай в ledger: `Решение: <что> — <почему> — <цена ошибки>`.

## Реализация

Один воркер на связанную подзадачу, модель по таблице. Вне простого пути лид может внести до трёх связанных правок файлов без новой логики; они тоже входят в область ревью. Воркер соблюдает назначенную область записи; необходимость другого файла сообщает лиду, который уточняет назначение в рамках разрешённой задачи и сохраняет нужные исходные снимки. Новое разрешение пользователя требуется только при выходе за его запрос.

Принимай результат после чтения назначенного `report-<n>.md`; отсутствие отчёта обрабатывай по state.md. В ledger: `Подзадача <n>: done|blocked — <суть>`. Сомнения идут в линзы ревью. При техническом провале сначала уточни бриф, затем эскалируй только эту подзадачу Luna → Sol → Astra. Для рискованной задачи сразу Sol / xhigh. Права, данные и решения пользователя модель не заменяет.

## Независимое ревью

Для непростой задачи после завершения реализации назначь отдельного от исполнителя ревьюера Sol / high; рискованные области — Sol / xhigh. Список файлов собери из задания/плана, отчётов и фактических Git-изменений, включая untracked. Сравни исходно dirty файлы со снимками, не только с HEAD или списком status. Для продолжения после ready используй также снимок начала текущей дельты.

До каждого раунда сохрани HEAD, индекс, рабочий diff и содержимое либо хеши затронутых файлов, включая untracked. Ревьюер только читает проект и записывает отчёт. После него сам сравни дерево со снимком, проверь новые файлы; не доверяй только `touched`. Если ревьюер изменил проект, это нарушение и непроверенный результат: не откатывай вслепую и не объявляй ready.

Раунд 1: ревьюер проверяет поведение, вызывающие пути, контракты, ошибки и полезность тестов. Вкус и стиль не находки. Находки чинит исходный воркер через `followup_task`; если автором был лид, исправления ведёт лид. Раунд 2: тот же ревьюер через `followup_task` проверяет исправления, затронутое поведение и новые дефекты в этой дельте. Отчёт каждого раунда — новый `review-<r>.md`; номер и расход лимита сохраняй до запуска. Принятое пользователем исключение передай как `Решение:` с риском.

Закрыто, когда `open` пуст, исправления проверены, адресные проверки зелёные, verdict `ready` и ревьюер не менял проект. **Максимум два начатых раунда на дельту**, в том числе после сбоев и финальных проверок. Не сошлось — перечисли остаток и предложи эскалацию без третьего запуска. В запросе только на чтение находки завершают аудит; исправления не начинай.

## Закрытие

После принятого ревью (либо короткого пути простой задачи) выполни необходимые проектные стадии по документу тестирования из `AGENTS.md`/`CLAUDE.md`, иначе по фактическим командам проекта. Стадии идут последовательно: БД и каталоги миграций могут быть общими. Длительную команду веди через exec-сессию и чтение её результата, сообщая пользователю о ходе работы.

Красный прогон из-за кода передай тому же воркеру, затем ревьюеру в оставшемся лимите. Не маскируй исправление новой дельтой. Внешний блокер зафиксируй без неизменных повторов. После исправлений повтори упавшие, затронутые и ранее пропущенные стадии. Зелёную стадию повторяй лишь при изменении её кода, зависимостей или окружения. Если команда даже с кодом 0 изменила результат задачи, проверь новую дельту в оставшемся лимите. Выполни проектный чеклист закрытия.

Итог: что сделано; запрошенные модели/effort и отдельно подтверждённые runtime (иначе «не подтверждено»); найдено → исправлено по раундам; проверенный HEAD и diff; команды и фактические результаты, пропуски с причинами, решения и остаток. Несколько прогонов — составной результат, не единый PASS. Коммит и публикация — только в пределах уже данного разрешения, с сохранением исходного индекса. Новое задание пользователя продолжает режим с новым критерием и проверками.
